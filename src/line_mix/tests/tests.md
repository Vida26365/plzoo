# Tests

`line_mix.exe` stops a file at its first error and exits with a non-zero code.
So one passing file can hold many commands, but every failing case needs its own file.

## Layout
```
src/line_mix/tests/
  run_tests.sh          # runs everything, prints PASS/FAIL, exit 1 if any FAIL
  pass/<name>.line_mix  # must run without errors
  pass/<name>.expected  # exact stdout ("value : type" lines)
  fail/<name>.line_mix  # must stop with an error; line 1: # expect: <kind>
  TODO/                 # minimal examples of known bugs (see TODO/README.md), not run by the script
```
`<kind>` is one of `Syntax error`, `Type error`, `Linear error`, `Runtime_error`.

## Script (`run_tests.sh`)
1. `dune build` from the repo root. Stop if the build fails.
2. For each `pass/*.line_mix`: run `line_mix.exe -n file`.
   It passes if the exit code is 0 **and** stdout equals `.expected` (`diff`).
3. For each `fail/*.line_mix`: run it the same way.
   It passes if the exit code is not 0 **and** stderr contains the `<kind>` from line 1.
4. Print one line per test, then a summary `N passed, M failed`. Exit 1 if M > 0.

Use `-n` so the runner never opens the interactive toplevel.
Create `.expected` once by running the file and checking the output by hand.

## Syntax the tests rely on
- Each command ends with `;`, and comments start with `#`.
- Function types use `-o`. Lambdas use `->`: `fun x : Int -> e`.
- `let rec f : Int -o Int = fun x : Int -> ...;`: the annotation is required.
- Linear (use exactly once): `File`, `*`, `&`, `+`, `Arr`.
  Unrestricted: `Int`, `Bool`, `Str`, `Unit`, functions.
- There is no `!` (bang) syntax yet, so there are no tests for it.

## Pass tests (one file per topic)
| file | covers |
|---|---|
| arith | `+ - * / %`, negative literals, precedence |
| bool | `true/false`, `=`, `<`, `if` (compare with = also the types that are not integers)|
| let | toplevel `let`, `let x : t =`, `let ... in`, reusing unrestricted vars |
| fun | `fun`, application, currying, higher-order, annotation `(e : t)` |
| rec | `let rec` with a base case, call after definition |
| pair | `(a, b)`, `match p with (x, y) ->` and `x, y ->` |
| sum | `(inl e : t + s)`, `match ... inl / inr` |
| with | `e1 & e2`, `fst`, `snd` |
| array | `[..]`, `make`, `length`, `lookup`, `set`, threading the array |
| string | literals, `^`, escapes |
| file | `open`/`write`/`read`/`close` on a temp file |

| file | expect |
|---|---|
| syn_missing_semi | Syntax error |
| syn_rec_no_annot (`let rec f = ...`) | Syntax error |
| syn_arrow_in_type (`Int -> Int`) | Syntax error |
| type_plus_bool (`1 + true`) | Type error |
| type_if_branches | Type error |
| type_unbound_var | Type error |
| type_apply_nonfun | Type error |
| type_inl_no_annot | Type error |
| type_eq_diff_types (`1 = true`) | Type error |
| type_eq_diff_arrays (`[1, 2] = [true, false]`) | Type error |
| lin_eq_used_twice (`a = a`, a linear) | Type error (unbound variable) |
| run_eq_fun (comparing functions) | Runtime_error |
| lin_pair_unused (`fun p : Int * Int -> 1`) | Linear error |
| lin_pair_twice | Linear error |
| lin_file_not_closed | Linear error |
| lin_file_closed_twice | Linear error |
| lin_if_diff_resources | Linear error |
| lin_redefine_unused (`let p = (1,2); let p = (3,4);`) | Linear error |
| run_div_zero (`1 / 0`) | Runtime_error |

`Runtime_error` is an uncaught OCaml exception, not a `Zoo.error`. It prints
`Fatal error: exception Interpret.Runtime_error(...)` and exits with code 2.
To get a normal `Runtime error: ...` message, raise it with `Zoo.error ~kind:"Runtime error"`.

## Verification
- Run `src/line_mix/tests/run_tests.sh` and check that everything is PASS.
- Sanity check: break one `.expected` file and confirm the script reports FAIL and exits 1.

## Report

### Equality on types that are not Int
**Pass test:** `pass/bool.line_mix` with `bool.expected`
- Covers `true`/`false`, `=` and `<` on integers, and `if`.
- Covers `=` on `Bool`, `Unit`, `Str`, pairs and arrays: equal, different, different lengths, and arrays of pairs.
- Covers `a = b` where both are linear array variables.
- `bool.expected` was generated by running the file, and all 22 output lines were checked by hand.

**Fail tests** in `fail/`:

| file | what it does | expects |
|---|---|---|
| type_eq_diff_types | `1 = true` | Type error |
| type_eq_diff_arrays | `[1, 2] = [true, false]` | Type error |
| lin_eq_used_twice | `a = a`, where `a` is a linear array | Type error |
| run_eq_fun | compares two functions | Runtime_error |

`lin_eq_used_twice` is really a linearity mistake, but the checker reports it as
`Type error: unbound variable a`, because the first `a` removes the variable from the context.
If it should be reported as a `Linear error`, the expectation needs to change.

### Bugs found (not covered by tests yet)
1. **Sum values can't be created.** `(inl 1 : Int + Int)` gives `Type error: cannot infer the type of inl e`.
   The `Annot` case in `infer` (`type_checker.ml`) calls `infer` on the expression instead of
   `check ctx t lty`, so the annotation is never used. `let s : Int + Bool = inr true;` breaks the
   same way, because it is parsed into an `Annot`. This also blocks the planned `sum` tests.
2. **Comparing `&` values crashes.** `(1 & 2) = (1 & 2)` hits `assert false` in `equal_value`
   (`interpret.ml:81`). There is no `VWith` case there. Decide whether `&` values can be compared
   at all; if not, the type checker should reject it.
3. **Comparing `inl x` with `inr y` would hit the same `assert false`.** It can't be reached yet
   because of bug 1, but it should return `false`.
